# 企业知识中心系统建设方案
## —— 面向人员使用、面向 Agent 开放、支持模块化积木式扩展

**文档用途**：用于指导 Codex / Cursor 等代码智能体完成系统架构设计、MVP 开发及后续模块扩展。  
**建设原则**：先做最小可用核心，再通过标准模块逐步叠加能力；知识系统首先服务于人，同时通过标准 API / MCP 向 Agent 提供知识访问能力。  
**建议项目代号**：Knowledge Center / Knowledge Hub / Knowledge Engine（内部可任选其一）

---

# 1. 建设目标

本系统定位为企业内部统一知识中心，不以“AI 问答”或“RAG 平台”为核心，而以企业知识的创建、组织、管理、检索、使用和开放为核心。

系统需要同时服务两类使用者：

1. **人员用户**
   - 创建、编辑、浏览、搜索企业知识；
   - 按空间、目录、标签、专题等方式组织知识；
   - 管理知识版本、权限、状态和生命周期；
   - 收藏、订阅、评论、引用、分享知识；
   - 通过普通搜索或 AI 辅助能力查找知识。

2. **Agent / AI / 外部系统**
   - 通过标准 API 检索知识；
   - 获取知识正文、元数据、版本及关联关系；
   - 查询最新有效版本；
   - 获取来源及引用信息；
   - 通过 MCP 将知识中心作为 Agent 工具使用；
   - 后续可扩展 RAG、GraphRAG、企业搜索、智能问答等能力。

系统不是单独的 Wiki，也不是单独的 RAG 系统，而是：

> **以“知识”为核心资产，以人为主要用户，同时向 AI 和 Agent 提供标准知识服务的企业知识基础平台。**

---

# 2. 核心设计原则

## 2.1 人优先，AI 兼容

系统首先必须是一套正常、完整、好用的企业知识管理系统。

AI 能力不能成为系统成立的前提。

即使关闭所有 LLM、Embedding、RAG 模块，系统仍需能够正常完成：

- 知识创建；
- 知识编辑；
- 知识浏览；
- 全文搜索；
- 权限控制；
- 版本管理；
- 知识组织；
- 生命周期管理；
- API 查询。

AI 是知识的消费者之一，而不是知识本身。

---

## 2.2 微内核 + 模块化

核心系统尽量保持精简。

Core 只负责稳定、不容易变化的基础能力：

- 用户与组织；
- 权限；
- 知识对象；
- 知识空间；
- 版本；
- 模块注册；
- 事件机制；
- 配置；
- API 基础框架。

其他能力尽量模块化：

- Markdown 编辑器；
- 文件导入；
- PDF 解析；
- OCR；
- 全文搜索；
- 向量搜索；
- AI 问答；
- Embedding；
- Reranker；
- MCP；
- Git 同步；
- 网页采集；
- 知识图谱；
- Agent 接入；
- 审批；
- 评论；
- 推荐；
- 自动标签。

---

## 2.3 积木式组合

模块之间不得形成大量直接依赖。

每个模块必须明确：

- 输入；
- 输出；
- 对外接口；
- 依赖能力；
- 事件；
- 配置项；
- 生命周期。

最终能够像积木一样组成不同产品形态。

例如：

### 组合 A：基础 Wiki

```text
Knowledge Core
+ Knowledge Space
+ Editor
+ Full-text Search
+ Permission
+ Version
```

### 组合 B：企业知识中心

```text
基础 Wiki
+ File Import
+ Metadata
+ Lifecycle
+ Audit
+ Advanced Search
```

### 组合 C：AI 知识中心

```text
企业知识中心
+ Embedding
+ Vector Search
+ Reranker
+ AI Assistant
```

### 组合 D：Agent 知识基础设施

```text
企业知识中心
+ Knowledge API
+ MCP
+ Agent Tools
```

---

## 2.4 知识与索引分离

必须明确区分：

1. 原始文件；
2. 知识正文；
3. 知识版本；
4. 知识片段；
5. 搜索索引；
6. 向量索引。

Embedding、Chunk、全文索引都属于派生数据。

禁止将向量数据库作为知识的唯一存储。

原始知识必须始终可以独立恢复。

# 4. Core 核心能力

Core 中只保留必须长期稳定的能力。

建议首版 Core 包含以下模块：

## 4.1 Identity

负责：

- 用户；
- 用户组；
- 组织机构；
- Role；
- 登录；
- Token；
- OIDC 预留。

MVP 可先使用本地账户。

---

## 4.2 Permission

权限模型建议首版使用：

**RBAC + Resource ACL**

支持：

- 空间权限；
- 知识权限；
- 管理员权限；
- 编辑权限；
- 阅读权限。

权限至少预留以下能力：

```text
owner
admin
editor
viewer
```

后续可扩展：

- 部门权限；
- 动态规则；
- ABAC；
- 密级；
- 数据范围。

所有 Agent API 必须复用同一套权限逻辑。

---

## 4.3 Knowledge Space

Space 是最上层知识组织单位。

示例：

```text
研发中心
行政制度
产品知识
项目知识
培训资料
技术知识
```

一个知识必须属于至少一个 Space。

Space 包含：

- id；
- name；
- description；
- owner；
- visibility；
- settings；
- created_at；
- updated_at。

---

## 4.4 Knowledge

Knowledge 是系统的核心业务对象。

建议将“知识”而不是“文件”作为核心抽象。

一个 Knowledge 可以来源于：

- 在线创建；
- Markdown；
- PDF；
- Word；
- 网页；
- API；
- Git；
- 外部系统。

核心字段建议：

```text
id
space_id
title
slug
summary
content
content_type
knowledge_type
source_type
source_uri
owner_id
status
visibility
current_version_id
created_at
updated_at
published_at
expired_at
```

knowledge_type 首版建议：

```text
article
document
faq
note
manual
policy
```

后续允许模块注册新的知识类型。

---

## 4.5 Knowledge Version

任何正式知识修改后均形成版本。

```text
knowledge_versions
├── id
├── knowledge_id
├── version_number
├── title
├── content
├── metadata
├── created_by
├── created_at
└── change_summary
```

必须支持：

- 查看历史版本；
- 比较版本；
- 恢复版本；
- 获取最新版本。

Agent 默认访问最新有效版本。

---

## 4.6 Metadata

Metadata 采用：

**固定字段 + JSONB 扩展字段**

不要为每种知识类型建立一套表。

例如：

```json
{
  "department": "研发中心",
  "author": "xxx",
  "effective_date": "2026-01-01",
  "security_level": "internal",
  "keywords": ["AI", "知识中心"]
}
```

模块可以注册自己的 Metadata Schema。

# 5. 模块体系设计

系统应提供统一 Module SDK。

每个模块必须提供 manifest。

示例：

```yaml
id: ai-rag
name: AI RAG
version: 0.1.0
type: service

requires:
  core: ">=0.1.0"
  modules:
    - search

permissions:
  - knowledge.read

events:
  subscribe:
    - knowledge.updated
  publish:
    - ai.answer.generated

config:
  model:
    type: string
  top_k:
    type: integer
    default: 8
```

# 7. 模块生命周期

统一模块状态：

```text
installed
enabled
disabled
error
updating
```

建议生命周期：

```text
install()
initialize()
start()
stop()
reload()
upgrade()
uninstall()
healthCheck()
```

MVP 不要求实现真正的进程内动态代码加载。

第一阶段推荐：

> **配置级热切换 + 独立服务级热插拔**

即：

- 模块可以启用 / 禁用；
- Provider 可以切换；
- 外部模块作为独立服务运行；
- Core 通过 HTTP / gRPC 调用。

不建议第一版实现高风险的任意代码热加载。

# 8. Event Bus

模块之间优先通过事件解耦。

核心事件建议：

```text
knowledge.created
knowledge.updated
knowledge.deleted
knowledge.published
knowledge.expired

version.created

file.uploaded
file.parsed

search.index.requested
search.index.completed

module.installed
module.enabled
module.disabled
```

例如：

```text
knowledge.updated
      │
      ├──> Search Module → 更新全文索引
      │
      ├──> Embedding Module → 更新向量
      │
      └──> Audit Module → 记录日志
```

第一版 Event Bus 可使用进程内事件机制。

后续升级：

```text
Redis Streams
RabbitMQ
Kafka
```

禁止 MVP 阶段过早引入 Kafka。

# 9. Pipeline

知识处理流程必须支持配置化。

基础 Pipeline：

```text
Source
  ↓
Parser
  ↓
Cleaner
  ↓
Metadata
  ↓
Storage
  ↓
Index
```

AI Pipeline：

```text
Source
  ↓
Parser
  ↓
Cleaner
  ↓
Chunker
  ↓
Embedding
  ↓
Vector Index
```

每个 Space 可绑定不同 Pipeline。

后期管理界面可支持积木式编排。

MVP 先使用 JSON / YAML 配置即可。

示例：

```yaml
pipeline:
  - parser: markdown
  - processor: clean
  - processor: chunk
    config:
      chunk_size: 800
  - processor: embedding
  - indexer: vector
```

**PostgreSQL**

主要表：

```text

space_members

knowledge

knowledge_tags

knowledge_relations

attachments

module_configs

```



# 12. Search 设计

搜索是知识中心的核心能力之一。

首版：

```text
PostgreSQL Full Text Search
```

第二阶段：

```text
OpenSearch
```

搜索接口必须统一：

```http
GET /api/search?q=xxx
```

返回：

```json
{
  "items": [
    {
      "knowledge_id": "",
      "title": "",
      "snippet": "",
      "score": 0,
      "source": "",
      "version": ""
    }
  ]
}
```

未来 Hybrid Search 仍使用同一 API。

# 13. Agent API

Agent API 不应该只有：

```text
ask(question)
```

而应该提供原子知识能力。

建议首批：

```http
GET /api/agent/spaces

GET /api/agent/knowledge/{id}

GET /api/agent/knowledge/{id}/latest

GET /api/agent/knowledge/{id}/versions

GET /api/agent/search

GET /api/agent/related/{id}
```

建议另外提供：

```http
POST /api/agent/search
```

请求：

```json
{
  "query": "xxx",
  "space_ids": [],
  "types": [],
  "limit": 10
}
```

Agent 返回内容必须带：

```text
knowledge_id
title
content/snippet
version
source
updated_at
```

Agent 权限不得绕过普通用户权限体系。

# 14. MCP

MCP 作为后续独立模块，而不是 Core 强依赖。

推荐 Tools：

```text
search_knowledge

get_latest_knowledge
list_spaces
get_related_knowledge
```

推荐 Resources：

```text
knowledge://{knowledge_id}

knowledge://space/{space_id}
```

MCP 调用底层 Knowledge Service，不允许直接访问数据库。

# 20. MVP 暂不实现

以下能力不要进入第一轮开发：

- 复杂工作流；
- BPM；
- 知识图谱；
- GraphRAG；
- Kafka；
- Kubernetes；
- 多租户；
- 复杂 ABAC；
- 复杂推荐系统；
- 在线多人协同编辑；
- AI Agent 自动写知识；
- 插件市场；
- 任意代码在线热加载；
- 微服务拆分；
- Neo4j；

# 24. 开发约束

Codex / Cursor 开发时必须遵守：

1. Core 不依赖任何具体 LLM。
2. Core 不依赖 OpenAI SDK。
3. Core 不依赖具体 Vector DB。
4. Core 不依赖具体 Parser。
5. Core 不依赖具体 Search Engine。
6. AI 模块不可直接访问数据库。
7. MCP 模块不可直接访问数据库。
8. 所有业务统一通过 Service Layer。
9. 所有 Agent API 必须执行权限检查。
10. 模块不可直接修改 Core Schema。
11. 模块之间禁止随意 import 对方内部实现。
12. 跨模块调用优先使用 Interface / Event。
13. 数据删除优先使用软删除。
14. 所有知识修改产生版本。
15. 所有 API 提供统一错误格式。
16. 所有核心能力必须有单元测试。
17. MVP 保持 Monolith，不要提前微服务化。

# 26. 首版验收标准

MVP 完成后必须能够完成以下完整流程：

```text
管理员创建用户
↓
创建知识空间
↓
给用户授权
↓
用户登录
↓
创建 Markdown 知识
↓
发布
↓
系统自动产生 Version 1
↓
修改
↓
自动产生 Version 2
↓
另一用户搜索
↓
打开知识
↓
查看版本
↓
Agent 使用 API 搜索该知识
↓
Agent 获取最新版本正文
```

并满足：

- 无权限用户无法通过 UI 查看；
- 无权限用户无法通过 API 查看；
- 无权限 Agent Token 无法获取；
- 停止 AI 模块不影响系统正常工作；
- 停止 Search 扩展模块不影响 Knowledge CRUD；
- Core 不包含任何具体模型实现。
